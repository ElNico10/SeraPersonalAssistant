# Keeping her prompts small

Settings live in `efficiency_config.json` (re-read when the file changes). Code: `notebook.py`, plus the marked spots in `discord_bot.py`.

**The notebook.** Long things are written to `SeraWorkspace\notebook\<chat id>.jsonl` and replaced in her history by one line:
`[Saved to your notebook as #14 (tool result: read_file..., 2300 characters). It begins: "..." Use look_back(14) to read the rest.]`
- Messages older than the newest 6 and longer than 800 characters are moved (plans, tool results, long replies, long messages). The person's `[Name]:` tag stays.
- A file someone attaches is shown to her in full for that one answer; afterwards the chat keeps a note and the first 200 characters.
- `look_back` is only offered to her once the chat has entries. `look_back(14)` reads one (6000 characters at a time, with an `offset` to continue); with no number it lists the latest. Each chat can only read its own notebook. 300 entries are kept per chat.

**One check instead of three.** `triage()` asks once: is it for her, and is it chat, a plan or code. If the answer can't be read, or `merged_triage` is false, the old separate checks run. The "what"-style guard (short message without code words is never code) still applies.

**A stable start.** Her notes about people go just before the newest message (not at the top), and the history is cut once, from 31 down to 20 messages, not by one every turn. That keeps the start of the prompt the same between messages so the model (or a paid API's prompt cache) can reuse it.

**Smaller things.** Unclear one-word checks retry twice, not three times (`classify_retries`). The "multi-step workflow" trigger matches whole words, so "misstep" or "rebuild" no longer set it off. Voice calls were not changed.

## Claude as the coding agent (owner only)

`!agent` (owner only; anyone else gets the usual refusal): `!agent claude` sends the owner's coding jobs to Claude Code, `!agent local` puts everything back on the local agent, `!agent model haiku|sonnet|opus|auto` forces a model or hands the choice back to her, `!agent` shows status. It is memory only: every restart is back on the local agent.
- A job only goes to Claude if it is the owner's. Whoever else might be allowed to delegate in future always gets the local agent.
- Which model: the owner's `!agent model` first, then a model named in the message ("use opus for this"), then how hard she judged the job (`easy` -> haiku, `normal` -> sonnet, `hard` -> opus; edit `agent_config.json` to change the mapping or the model ids). A Claude job is sent back at most once (`claude_max_attempts`).
- The Claude call (`_agent_claude`) is limited to the file tools, uses a short system prompt, and skips user hooks, plugins and connectors: a two-turn file job measured ~70,000 input tokens with the plain call and ~9,000 this way. Each attempt writes `CLAUDE USAGE: model | input | cached | output | ms` to the job log.
- **Kept-open sessions** (`claude_sessions.py`, `persistent_sessions` in `agent_config.json`): a model's Claude process is started the first time a job needs it and then stays open, so later jobs skip the process start and the system-prompt/tool intake (measured: ~294 new input tokens per job instead of ~1,400, ~3.5 s instead of ~5 s). A model nobody asks for is never started. `!agent local` closes them all (one in the middle of a job closes when the job ends); the bot exiting closes them too. The cost: a session remembers its earlier jobs, so it is replaced after 8 jobs (`session_max_jobs`) or when a job's input passes 40,000 tokens (`session_max_context`). A session that dies is replaced and the job retried once. `!agent` shows the open sessions.
  - Each new job starts with `/clear` sent into the open session (the process, system prompt and tool list stay; what it remembers goes), so the context does not grow: six real jobs in a row measured ~9,100-9,500 input tokens each, flat, ~3.5 s each. A retry of the same job is not cleared, so the agent remembers what it tried. The full record is on disk anyway: the files it wrote, the job log, and the last job's report that `build_task` passes along.
  - **Saved before wiped.** Every Claude attempt is written (no model involved) to `.history/job-<n>-attempt-<a>.md` in the agent's folder: what it was asked, each step (what it said, each tool call with its arguments clipped, a clipped tool answer) and how it ended, plus a one-line-per-attempt `.history/INDEX.md`. The next job's prompt gets two sentences pointing at `INDEX.md` and saying to read a transcript only if the task depends on an earlier job. `.history` is a dot-folder, so change detection, review and the file list skip it. The newest 50 are kept (`history_keep`); `save_transcripts: false` turns it off; a failure to write never fails a job.

## Sera's view of the agents' work (owner only, read-only)

`look_at_agent_work` lets her look at what the agents have made, whichever agent is switched on, without handing anything off. `path` empty gives an overview; `agent/` is the agents' working folder (including `.history/`), `jobs/` is the job logs; a file path reads it (6,000 characters at a time, `offset` continues). Only those two folders are reachable (checked after resolving links and junctions; `..`, other drives and sibling folders are refused), and nothing can be changed through it. The tool is offered only in the owner's chat and only once an agent has left something there; what she reads is not posted to the chat, she answers from it.

## `!help`

`!help` (or `!commands`) lists the commands. The owner gets all of them; everyone else gets a short list of what they can use. The voice and picture lines are the ones `!vc` and `!image` print themselves. `help_test.py` fails if a new `!command` is routed in `on_message` but missing from the owner's list.

**Looking is not a job.** When the owner asks her to look at what the agents made ("is there a regex file in the agents folder?", "what files has the agent made?"), `looks_like_agent_view` sends it straight to her own view: no hand-off, no plan, and her notes-folder and hand-off tools are left out so she can't pick them by mistake. Requests to change or create something ("create a regex file in the agents folder") are still jobs; a question about the past ("did the agent create ...?") is a look. The combined check's CODE rule and her reading step now also say that checking existing files is not code.

**Which model, in the log.** A job's log and the console now say exactly which model is in use. At the start: the console prints `Job #3 attempt 1 starting on Claude opus (claude-opus-5-5)` (or `the local agent (<model>)`), and the job log's first line ends with the model id and tier. After each Claude call the job log has `CLAUDE MODEL: asked for <id>, answered by <id>` taken from what the CLI reports (with `(NOT the model asked for)` if they differ, or a note when the CLI doesn't say), followed by the `CLAUDE USAGE` tokens line; the console's finishing line adds `(answered by <id>)`.

**Asking an agent to look is a job.** "have an agent verify the code in the regex files", "get the specialist to check the files", "make claude look at ..." are requests for an agent to do something, so they are still handed off even though the verbs are looking verbs (`ASKS_AN_AGENT` in `discord_bot.py`). Her hand-off announcement is also told what the job really runs on (the Claude tier, or the local agent) and that she can't set a model or effort level from chat, so she stops promising "Sonnet 5.5 on low effort". Remember `!agent claude` after every restart: a restart puts jobs back on the local agent.

**The agent is told it is the agent.** The task Sera passes along carries the user's own words, which can include things meant for her ("have an agent verify...", "try sonnet on low effort"). The Claude agent used to answer "I can't start an agent or pick a model". Now the task, and the Claude agent's system prompt, say it IS the agent and to ignore talk of starting an agent, choosing a model or an effort level, and her reading of the request is told to leave those out.

**A model you name is the model used.** `asked_model` now recognises how people really ask ("have sonnet 5.5 go through it", "try opus", "get haiku on it", "sonnet 5.5 please", "use opus"), and it applies on every route (the hand-off, and the plan-then-tool route), so her own easy/normal/hard guess can no longer override it. Order: `!agent model` forced > a model named in the message > her difficulty guess. A bare word like "write a sonnet" doesn't count.

**Effort level for Claude jobs.** Say it in a message ("use sonnet on low effort", "high effort please") or force it with `!agent effort low|medium|high|xhigh|max|auto`; the forced one wins, and with neither the CLI's own default is used (nothing is guessed). It is passed to the CLI as `--effort` and shown everywhere: the announcement, the console (`starting on Claude sonnet (claude-sonnet-5-5) at low effort`), the job log (`effort low`, or `effort default (not set)` in the `CLAUDE MODEL` line), and `!agent` (open sessions are listed per model and effort). A kept-open session is per model AND effort, since effort is fixed when a session starts; the local agent never gets an effort level.

## The general sandbox (any command, any installed language)

`agent_sandbox.run_command` runs an arbitrary shell command in a throwaway Docker container: no network, not root, no capabilities, read-only filesystem, the agent's folder mounted read-only and copied into a 256 MB scratch space, 1 GB of memory, 2 CPUs, 256 processes, 30 s by default (up to 120). Nothing it does is kept, so agents edit with their file tools and run in the sandbox. It uses the multi-language image `sera-sandbox:latest` when that is built (recipe: `sandbox/Dockerfile`, one `docker build`) and the Python image until then, and tells the agent what it has when a command isn't found.
- **Claude agent:** has no shell (Bash was never given and still isn't). Its one way to run code is a single tool, `mcp__sandbox__run`, served by `sandbox_mcp.py` (a small MCP server the bot hands the CLI with `--mcp-config`, with `--strict-mcp-config` keeping it the only connector). Its prompt now says so.
- **Local (Qwen) agent:** gets a `run_command` tool next to `run_python`.
- **Sera herself** is never given either tool.
- No network at run time means no `pip install` / `npm install`: only what is baked into the image.

**The multi-language image is built** (`sera-sandbox:latest`, 3.94 GB, built in about 3.5 minutes from `sandbox/Dockerfile` on Debian 13). The bot uses it automatically (re-checked about once a minute). Installed: Python, C, C++ (gcc, g++, make, cmake), C# (mono: mcs, mono), Go, Rust (rustc, cargo), Java (javac, java), JavaScript (node), TypeScript (tsc), R (Rscript), Ruby, PHP, Lua, Perl, Fortran (gfortran), SQLite, git, jq, curl, tidy, and a headless Chromium behind `render FILE.html` (loads the page, runs its scripts, prints the final DOM and the page's console errors); `node-jsdom` is there for quick DOM tests. HTTP servers can be started and called inside one container (loopback works; there is no outside network). To add a language, add its package to the Dockerfile and run `docker build -t sera-sandbox:latest SeraFunctionality/sandbox` again.

## Pings (@Name in her own replies)

When she writes `@Name` in a reply, `add_mentions` turns it into a real Discord ping if Name is exactly someone's Discord name (the `name` in people.json; capitals don't matter; names with spaces work). It never resolves a nickname she gave someone (an `@Sam` stays text if Sam is only what she calls the owner), never a part of a name, never `@everyone`, `@here` or a role, never inside code or a quoted line, never the person she is answering (the reply already notifies them), and only `mention_limit` (2) per message; a name two people share is skipped. Only her own words go through it (her replies, the hand-off announcement, and lines she types in the chat from a voice call, owner only): tool output, files and agent reports never do. Her notes now show `Sam (Discord name: samuel_99)` and tell her to ping with the Discord name, never a nickname. `mention_names: false` in `efficiency_config.json` turns it off.
